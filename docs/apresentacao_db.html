Princípio Central

Encapsulamento Total

❌ O que a aplicação NÃO faz

-- NUNCA enviado pela rede
INSERT INTO Cliente (nome, cpf) VALUES (?, ?)
UPDATE Quarto SET preco = ? WHERE id = ?
SELECT * FROM Funcionario WHERE login = ?

✅ O que a aplicação FAZ

# Python — única forma de acesso
call_proc(conn, "sp_Cliente_Create",
          (nome, cpf, email, tel, end))

call_proc(conn, "sp_AtualizarPrecoQuarto",
          (id_quarto, novo_preco, id_executor))

query_view(conn, "vw_quartos_disponiveis")

Por que isso importa?

Toda regra de negócio vive no banco — qualquer cliente (app, Workbench, script) que tente burlar a aplicação ainda passa pelas mesmas validações.

SQL Injection impossível — não há concatenação de strings SQL. Parâmetros são vinculados pelo driver, nunca interpolados.

Controle de acesso no banco — mesmo um DBA mal-intencionado com acesso direto ao MySQL encontra as mesmas barreiras de perfil nas procedures.

Stored Procedure em Detalhe

sp_RegistrarReserva — Detecção de Sobreposição

CREATE PROCEDURE sp_RegistrarReserva(
  IN p_id_cliente INT, IN p_id_quarto INT,
  IN p_id_func INT,
  IN p_checkin DATE, IN p_checkout DATE)
BEGIN
  DECLARE v_conflitos INT;
  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    ROLLBACK; RESIGNAL;
  END;

  START TRANSACTION;

  SELECT COUNT(*) INTO v_conflitos
  FROM Reserva
  WHERE id_quarto = p_id_quarto
    AND status IN ('Confirmada','Efetivada')
    AND NOT (
      data_checkout_prev <= p_checkin
      OR data_checkin_prev >= p_checkout);

  IF v_conflitos > 0 THEN
    SIGNAL SQLSTATE '45000'
      SET MESSAGE_TEXT = 'Periodo sobreposto';
  END IF;

  INSERT INTO Reserva (...) VALUES (...);
  COMMIT;
END

Padrão Transacional

DECLARE EXIT HANDLER FOR SQLEXCEPTION
garante ROLLBACK automático em qualquer erro —
o banco nunca fica em estado parcial.

Detecção de Sobreposição

A condição NOT (checkout_prev ≤ checkin_new OR checkin_prev ≥ checkout_new) detecta qualquer tipo de sobreposição de período no mesmo quarto.

RESIGNAL

O erro é relançado para o Python via RESIGNAL — a mensagem do SIGNAL chega como RuntimeError e é exibida ao usuário sem expor detalhes internos.

Stored Procedures — Fluxo de Hospedagem

CheckIn · CheckOut · Consumo

sp_RealizarCheckIn

START TRANSACTION;
-- valida reserva Confirmada
-- valida quarto Disponivel
UPDATE Reserva
  SET status='Efetivada';
UPDATE Quarto
  SET status='Ocupado';
INSERT INTO Hospedagem (
  preco_diaria_aplicado
    = Quarto.preco_praticado
  -- snapshot do preço atual
);
COMMIT;

O preço é congelado no momento do check-in — reajustes futuros não afetam estadias em curso.

sp_RealizarCheckOut

START TRANSACTION;
-- valida status = 'Ativa'
-- calcula valor total
n_dias * preco_diaria_aplicado
+ SUM(qtd * preco_unitario_momento)

UPDATE Hospedagem
  SET valor_total_diarias,
      data_checkout_real,
      status='Finalizada';
UPDATE Quarto
  SET status='Limpeza';
COMMIT;

Usa preco_diaria_aplicado (snapshot) — faturamento histórico imutável.

sp_LancarConsumo

START TRANSACTION;
-- valida hospedagem Ativa

SELECT preco_praticado
  INTO v_preco
FROM Produto_Servico
WHERE id = p_id_ps;

INSERT INTO Consumo (
  preco_unitario_momento
    = v_preco  -- snapshot
);
COMMIT;

Preço do produto congelado no momento do consumo — mesma invariante de snapshot.

Demo de Transações (99_demo_transacoes.sql)

Cenário 1 — COMMIT normal
Atualiza preço → trigger cria histórico → COMMIT confirma.

Cenário 2 — ROLLBACK explícito
Atualiza preço → cria histórico → ROLLBACK → tudo desfeito, preço original restaurado.

Cenário 3 — SAVEPOINT parcial
Atualiza dois quartos → ROLLBACK TO SAVEPOINT → só o segundo é desfeito.

Garantia de Atomicidade

Um check-in envolve 3 tabelas (Reserva, Quarto, Hospedagem). Sem transação, uma falha entre os UPDATEs deixaria o banco inconsistente. O handler garante que ou tudo ocorre, ou nada ocorre.

Triggers

2 Triggers — Invariante do Histórico de Preço

trg_preco_inicial_quarto — AFTER INSERT

CREATE TRIGGER trg_preco_inicial_quarto
AFTER INSERT ON Quarto
FOR EACH ROW
BEGIN
  INSERT INTO Historico_Preco (
    id_quarto, preco_praticado,
    data_inicio_vigencia,
    data_fim_vigencia)
  VALUES (
    NEW.id_quarto,
    NEW.preco_praticado,
    NOW(), NULL);  -- NULL = vigente
END

Todo quarto nasce com seu primeiro registro histórico de preço.

trg_atualiza_preco_quarto — AFTER UPDATE

CREATE TRIGGER trg_atualiza_preco_quarto
AFTER UPDATE ON Quarto
FOR EACH ROW
BEGIN
  IF OLD.preco_praticado <>
     NEW.preco_praticado THEN

    -- fecha vigência anterior
    UPDATE Historico_Preco
    SET data_fim_vigencia = NOW()
    WHERE id_quarto = NEW.id_quarto
      AND data_fim_vigencia IS NULL;

    -- abre nova vigência
    INSERT INTO Historico_Preco ...;
  END IF;
END

Por que trigger e não procedure?

A invariante "todo UPDATE de preço gera linha em Historico_Preco" é mantida pelo SGBD — protege mesmo alterações diretas via Workbench, scripts de migração ou qualquer outro cliente.

Segurança

Senhas · SHA2 · Controle de Acesso

SELECT id_funcionario, nome, perfil

Segurança — SQL Injection

Por que SQL Injection é impossível aqui

❌ Vulnerabilidade clássica

# Python vulnerável (NÃO é o que fazemos)
sql = f"SELECT * FROM Funcionario
       WHERE login = '{login}'"
cursor.execute(sql)

# Ataque: login = ' OR '1'='1
# Resultado: retorna todos os usuários

✅ Nossa abordagem

# Python — parâmetros vinculados pelo driver
cursor.callproc("sp_Login",
               (login, senha))

# O driver envia parâmetros separados
# do SQL — jamais concatenados.
# Não há SQL para injetar.

3 Camadas de Proteção

1. Sem SQL dinâmico
A app só chama procedures por nome fixo. Não existe string SQL montada em runtime.

2. Parâmetros vinculados
O mysql-connector usa placeholders internos. O MySQL recebe o valor como dado, não como código SQL.

3. Permissões mínimas
O usuário MySQL da app tem apenas EXECUTE em procedures e SELECT em views. Mesmo com credenciais expostas, não consegue fazer DROP, INSERT direto, ou SELECT em tabelas sensíveis.
